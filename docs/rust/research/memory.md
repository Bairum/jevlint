# Rust memory/resource semantic pack: research handoff

Original research phase (before implementation): research/proposal only. Live primary documentation was read; no repository changes, installs, provider calls, compilation, tests, formatters, Miri, sanitizers, or model checks were run during that phase. Paired fixtures below are concepts, not exercised tests. Candidate names/priorities are proposed Jevlint policy, not Rust standard rule names.

## Recommendation and scope

Prioritize the ecosystem's contextual resource/correctness concerns: observable cleanup errors, strong ownership cycles, runtime borrow/reentrancy failures, and unsafe invariants that safe clients can break. These are research priorities, not a claim that the current Jevlint extractor can reliably diagnose them by default. Borrow-checker diagnostics, syntactic unsafe documentation requirements, obvious clone redundancies, and formatting belong to existing tools. Do not replace soundness review with a safety-comment checker.

Rust's ownership system prevents many memory errors, not every resource leak, deadlock, logical race, or partially completed transaction. Unsafe Rust must uphold contracts for **every safe client**, including clients that panic, leak guards, or implement safe traits incorrectly. Safe-code business invariants are a different class of requirement: do not label a resource leak or inconsistent transaction UB without an actual memory-safety path.

### Tiers and priorities

- **T — tool-owned:** deterministic compiler/Clippy checks. Deduplicate rather than recreate with an LLM.
- **C — core semantic concern:** contextual review with a concrete path and known API/business contract; high-value research candidates, gated by supplied evidence rather than automatically default-enabled.
- **S — specialist semantic:** unsafe/FFI/pinning candidates. Opt-in/manual/deferred with current extraction; require adequate cross-file and platform context, output a counterexample or precise unproven obligation, never certify soundness.
- **A — advisory:** conditional API/performance recommendations; not correctness failures without documented requirements.
- **P0:** potential UB/unsound safe interface. **P1:** concrete resource, data-loss, panic, deadlock, or business-invariant bug. **P2:** avoidable work/API flexibility/maintainability tradeoff.

Normative strength is separate from priority: Reference and std unsafe API contracts describe required behavior; API Guidelines are ecosystem recommendations; std/Tokio performance advice is conditional; syntax preferences are disputed or optional.

## Evidence contract for every semantic finding

Require the operation and location, exact type and method resolution, violated documented invariant, a control-flow/caller path that makes it reachable, source link, relevant exceptions, and confidence. For unsafe code trace ownership, allocation provenance/layout, initialized region, aliasing, lifetime, mutation, panic/error paths, and deallocation. Read the implementing module and every relevant safe constructor/mutator/derived trait—not just the unsafe block. A comment saying `SAFETY: valid` is an assertion to check, not evidence of validity. Missing context should produce an explicit review obligation, not a fabricated bug or proof.

Needed project context: edition and MSRV/toolchain, `no_std`/allocator choices, target architecture/ABI/endian/alignment, panic profile, foreign headers/version/ownership contract, callback threading/reentrancy/lifecycle, runtime scheduling, library versus application API stability, and resource guarantees. Infer none of these from `extern "C"`, `Arc`, or the word `unsafe` alone.

### Current Jevlint capability gate (parent-supplied repository research)

Current Rust support extracts function/type units and limited same-file related type/impl context, but supplies no compiler typing, name resolution, or macro expansion. Rust method calls and `Type::qualified` calls do not resolve into direct callee context. Consequently, a method spelling such as `clone`, `flush`, `drop`, or `borrow_mut` does not establish the std API contract or its actual implementation. The candidate inventory below remains broad to reflect ecosystem concerns; these evidence requirements are not provided automatically by current extraction.

- M01/M10/M11 advisory API/performance choices need caller/consumer/type and workload information; opt-in, not reliable default defects.
- M02/M03/M06/M07/M08/M09/M25 need alias identity, graph/call paths, business/security requirements or runtime behavior. Manual/opt-in with explicitly supplied context; defer whole-program absence claims.
- M04/M05 can support narrow local review where explicit constructions and visible control flow establish the real API and failure path, but method-name matching is insufficient. Without that evidence, report an obligation rather than a definite missing-flush/destructor-panic violation.
- M12–M24 and M26 depend on unsafe contracts, complete API surfaces, macro-derived access, concrete types, threading, platform/foreign context, or lifetime/alias facts. Specialist/manual/deferred, never a reliable default soundness lint.
- Tool-owned checks stay tool-owned. A prompt cannot fill compiler/context gaps by confidence language. Parent verification of attribute/doc extraction and fixture semantics is still required before any implementation selection.

The safest near-term semantic pack can provide evidence-gated review prompts; it cannot claim typed callee inspection, expanded derived implementations, global ownership graph analysis, or universal soundness proof that the extractor does not deliver.

## Candidate inventory

### M01 — Ownership API forces unnecessary copying (A/P2)

**Trigger:** a function borrows an argument only to clone and retain it, or consumes an owned value only to inspect it and drop it, forcing known callers to clone. **Why:** caller control over copying/placement is an explicit API Guidelines recommendation, not a universal mandate for every consuming API. **Source:** [C-CALLER-CONTROL](https://rust-lang.github.io/api-guidelines/flexibility.html#caller-decides-where-to-copy-and-place-data-c-caller-control); [Book borrowing](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html).

**Exceptions:** consuming/builder APIs, ownership transfer that releases a resource, uniform trait signatures, intentional snapshots, task ownership, semver constraints, cheaply copied scalar values. Do not mechanically change public APIs. **Evidence:** body, exact Clone implementation/cost, representative callers, whether ownership really is retained, trait/API constraints. **Pair:** violation concept `store(&String)` always clones into owned storage while caller already owns an expendable String; passing `store(String)` moves it. Conversely, a read-only `measure(String)` requiring caller cloning versus `measure(&str)`. **Overlap:** function/API research; route obvious unused ownership/cloning cases to installed Clippy rather than generate duplicate findings.

### M02 — Cloning does not provide the promised independent state (C/P1)

**Trigger:** clone of `Arc<Mutex<T>>`, `Rc<RefCell<T>>`, or a derived wrapper is used as an isolated snapshot/transaction workspace, but its mutations affect the original. **Why:** Clone explicitly may share underlying data; derived Clone clones each field. [Clone contracts](https://doc.rust-lang.org/std/clone/trait.Clone.html#derivable), [Arc cloning](https://doc.rust-lang.org/std/sync/struct.Arc.html#cloning-references).

**Exceptions:** intentional shared ownership, observer handles, deduplicated immutable data, documented copy-on-write. **Evidence:** promised independence from API/tests/use, field types and Clone implementations, mutation path, aliasing consumers. **Pair:** violation clone shared account handle, modify clone, expect original unchanged; passing clone the locked inner value into a fresh owner when snapshot semantics require it. Do not demand deep copies merely because `.clone()` appears.

### M03 — Long-lived resource retained unnecessarily (C/P1; A/P2 if only a speculative memory cost)

**Trigger:** a guard/file/large buffer is retained after its required work, and a demonstrated subsequent operation needs its release or long-lived retention violates a known budget. **Why:** lifetimes of borrows are not destruction scopes; values with Drop remain until their actual drop scope. [Reference drop scopes](https://doc.rust-lang.org/reference/destructors.html#drop-scopes), [Mutex RAII](https://doc.rust-lang.org/std/sync/struct.Mutex.html).

**Exceptions:** lock needed for atomic transaction; cached capacity deliberately reused; handle must stay open; no observed consequential retention. **Evidence:** actual guard type and scope, use/drop order including temporary lifetime/edition rules, dependency of next action on release. **Pair:** violation retain mutex guard then invoke helper that locks same mutex; passing release in an inner scope before helper when the transaction permits. Separate this from a fixed rule that every lock scope must be short.

### M04 — Buffered output completion silently relies on Drop (C/P1)

**Trigger:** API returns success for required output while locally owned BufWriter is dropped without observing flush/completion errors. **Why:** BufWriter Drop attempts flushing but ignores its errors; explicit `flush` is documented as critical. [BufWriter](https://doc.rust-lang.org/std/io/struct.BufWriter.html), [into_inner](https://doc.rust-lang.org/std/io/struct.BufWriter.html#method.into_inner).

**Exceptions:** writer ownership handed back for later completion, intentionally best-effort output, explicit observed completion elsewhere. Flush is not file durability (`fsync`) and the rule must not claim it is. **Evidence:** output contract, ownership path, every successful return, whether buffer can contain unwritten data. **Pair:** violation function write_all then Ok, with sink failure only on flush; passing explicit `flush()?` or checked into_inner before Ok. **Overlap:** I/O/error handling; one finding, not separate “missing flush” and “ignored destructor error” reports.

### M05 — Panic-prone destructor loses cleanup or aborts (C/P1; S/P0 if it exposes invalid memory)

**Trigger:** Drop uses fallible operations with unwrap/expect/indexing/user callbacks while cleaning up a resource, with a demonstrated reachable failure or unwind path. **Why:** std recommends generally avoiding panics in Drop; a panic during unwinding can cause process abort. [Drop panics](https://doc.rust-lang.org/std/ops/trait.Drop.html#panics), [panic destruction](https://doc.rust-lang.org/reference/panic.html#unwinding).

**Exceptions:** deliberate invariant-reporting destructor, fail-fast/abort policy, operation proved infallible, correctly protected manual cleanup. Do not ban every unwrap in Drop by token match. **Evidence:** failure path, panic strategy, resource state, ownership of fields, whether additional manual drop could double-drop after panic. **Pair:** violation custom handle Drop closes using `.expect(...)`, invoked while another panic unwinds; passing best-effort nonpanicking Drop plus explicit fallible `close()` for required error reporting. Rust automatically drops ordinary owned fields; do not require redundant Drop implementations.

### M06 — Strong reference-count ownership cycle leaks a required resource (C/P1)

**Trigger:** reachable cycle of strong Rc/Arc ownership with no teardown path, while reclamation is expected. **Why:** strong cycles do not deallocate; Weak breaks non-owning backedges. [Arc Weak cycles](https://doc.rust-lang.org/std/sync/struct.Arc.html#breaking-cycles-with-weak), [Nomicon leaks](https://doc.rust-lang.org/nomicon/leaking.html).

**Exceptions:** deliberate process-lifetime graph, externally broken cycle, arenas/registries intentionally owning all nodes, required shared ownership rather than backlinks. Weak retains backing allocation, not the inner value; avoid claiming it frees all allocation metadata immediately. **Evidence:** whole ownership graph, edge strong/weak types, mutation that establishes cycle, teardown and expected resource lifetime. **Pair:** violation tree parent owns children and child owns parent strongly; passing Weak parent link with upgrade failure handled.

### M07 — Runtime borrow guard crosses reachable reentrant borrow (C/P1)

**Trigger:** Ref/RefMut remains alive across callback/reentrant helper/suspension that borrows the same RefCell incompatibly. **Why:** RefCell dynamically enforces borrows and panics on conflicts. [RefCell::borrow_mut](https://doc.rust-lang.org/std/cell/struct.RefCell.html#method.borrow_mut), [try_borrow_mut](https://doc.rust-lang.org/std/cell/struct.RefCell.html#method.try_borrow_mut).

**Exceptions:** callback cannot reenter; same-cell access compatible and shared; conflict is an intentional assertion; fallible borrow handled according to contract. Returning default values on borrow failure is not inherently a correct fix. **Evidence:** guard scopes and alias identity, callback call graph/reentrancy capability, borrow mode, conflict policy. **Pair:** violation event handler holds borrow_mut while calling listener that reads same cell; passing complete mutation/release first then notify. **Overlap:** [await_holding_refcell_ref](https://rust-lang.github.io/rust-clippy/master/index.html#await_holding_refcell_ref) owns direct await syntax; Jev should focus on otherwise-unrecognized reentrancy/context, acknowledging explicit-drop false positives documented by Clippy.

### M08 — Safe-code panic/error recovery exposes partially completed state (C/P1)

**Trigger:** multi-step state update calls a fallible/panic-capable user operation after first mutation and recovery continues with violated business invariants. **Why:** Nomicon distinguishes required memory-safety exception safety from recommended logical exception safety. [Exception safety](https://doc.rust-lang.org/nomicon/exception-safety.html), [Mutex poisoning is advisory](https://doc.rust-lang.org/std/sync/struct.Mutex.html#poisoning), [Tokio Mutex does not poison](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html).

**Exceptions:** partial progress is documented; failure terminates relevant state use; rollback/commit protocol; invariant explicitly allows intermediate state. **Evidence:** actual invariant, mutation sequence, fallible/callback path, observer after error/catch/retry; safe Rust inconsistency is not automatically UB. **Pair:** violation debit before callback validation, catch panic and reuse ledger without credit; passing compute/validate before commit or restore state with a correct guard. **Overlap:** error/transaction/concurrency domains.

### M09 — Allocation pressure from untrusted size exceeds contract (C/P1 when resource limit exists; A/P2 otherwise)

**Trigger:** external count/length drives reservation or buffering without applying documented input/resource bounds, or required allocation recovery is bypassed by infallible allocation. **Why:** Vec distinguishes initialized length from allocation capacity; `try_reserve` reports capacity overflow/allocator-reported failure and preserves contents. [Vec capacity](https://doc.rust-lang.org/std/vec/struct.Vec.html#capacity-and-reallocation), [try_reserve](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.try_reserve).

**Exceptions:** trusted bounded input, deliberate process abort on OOM, streaming already bounds total memory, limit enforced upstream. `try_reserve` is not a magical global OOM guarantee; other allocations/allocator policies remain relevant. No invented maximum capacity. **Evidence:** trust boundary, size arithmetic, workload/resource policy, upstream checks and subsequent allocation behavior. **Pair:** violation network length directly requests capacity despite specified maximum frame size; passing enforce that maximum and use fallible reservation if recovery is required. **Overlap:** security/input validation, not a universal with_capacity mandate.

### M10 — Avoidable hot-path copying/allocation (A/P2)

**Trigger:** repeated owned materialization/clone/reallocation whose necessity is disproved by actual consumers and whose hot-path or scale impact is established. **Why:** Clone may be expensive or cheap and may run arbitrary code; Vec capacity can avoid reallocation but amortized push is already O(1), capacity reuse is intentional. [Clone](https://doc.rust-lang.org/std/clone/trait.Clone.html), [Vec guarantees](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees), [C-CALLER-CONTROL](https://rust-lang.github.io/api-guidelines/flexibility.html#caller-decides-where-to-copy-and-place-data-c-caller-control).

**Exceptions:** snapshots, ownership across task/API boundary, Arc/Rc cheap sharing, clone avoids worse lock retention/lifetime coupling, optimizer removes copies, small cold-path costs, intentional bounded over-reservation. **Evidence:** exact type/Clone implementation, data size/frequency, caller ownership, runtime/performance requirement or measurement (none collected in this research). **Pair:** violation clone megabyte Vec on every read-only loop operation; passing borrow slice when ownership/lifetime permits. Advisory unless documented acceptance target is actually violated. Do not invent allocation counts from Rust source alone or say every iterator pipeline is allocation-free.

### M11 — Shared ownership choice mismatches actual threading contract (A/P2; S/P0 for unsafe overrides)

**Trigger:** Arc used only in provably single-threaded internal hot path; or unsafe Send/Sync claims try to make unsynchronized shared data thread-safe. **Why:** std conditionally recommends Rc for lower overhead without interthread sharing but explicitly allows Arc in libraries for consumer flexibility. Arc's atomic refcount does not make inner data thread-safe. [Arc thread safety](https://doc.rust-lang.org/std/sync/struct.Arc.html#thread-safety).

**Exceptions:** public Send-compatible API, multithreaded runtime requirements, future caller flexibility already part of API contract, sound synchronization in an unsafe wrapper. **Evidence:** whole owner movement/sharing, runtime and exported API bounds. **Pair:** advisory violation Arc-only local graph in measured single-thread hot path; passing Rc where it satisfies all consumers. Unsafe violation force Sync over RefCell with concurrently exposed borrows; passing synchronization-backed abstraction. **Overlap:** compiler Send/Sync checking and [arc_with_non_send_sync](https://rust-lang.github.io/rust-clippy/master/index.html#arc_with_non_send_sync); do not emit blanket Arc-to-Rc edits.

### M12 — Safe interface fails to enforce unsafe preconditions (S/P0)

**Trigger:** safe method can reach unchecked indexing, pointer access, arbitrary lifetime conversion, or manual destruction without establishing all unsafe callee requirements. **Why:** safe clients must not be able to trigger UB. [Reference soundness](https://doc.rust-lang.org/reference/behavior-considered-undefined.html), [safe/unsafe interaction](https://doc.rust-lang.org/nomicon/safe-unsafe-meaning.html), [Safety documentation recommendation](https://rust-lang.github.io/api-guidelines/documentation.html#function-docs-include-error-panic-and-safety-considerations-c-failure).

**Exceptions:** invariant established by private construction, genuinely safe wrapper checking/enforcing requirements, unsafe caller contract assigning a requirement to caller. Neither an unsafe signature nor a `SAFETY` comment excuses an internally violated requirement. **Evidence:** all safe constructors/mutators, type privacy, trait impls and invariants, operation docs, concrete safe client counterexample. **Pair:** violation safe get(index) calls get_unchecked on arbitrary index; passing checked get or validated bounds before unchecked operation. **Overlap:** [missing_safety_doc](https://rust-lang.github.io/rust-clippy/master/index.html#missing_safety_doc) checks section presence; semantic review checks completeness/correctness and enforceability, not comment presence.

### M13 — Unsafe state invalid during panic/error path (S/P0)

**Trigger:** raw read/move/length publication/temporary duplicate ownership occurs before panic-capable generic Clone/Ord/callback/error handling restores valid state. **Why:** minimum exception safety is mandatory in unsafe code. [Nomicon exception safety examples](https://doc.rust-lang.org/nomicon/exception-safety.html), [Vec::set_len](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.set_len), [Mutex poisoning caveat](https://doc.rust-lang.org/std/sync/struct.Mutex.html#poisoning).

**Exceptions:** operation proven not to panic, valid-state guard, no invalid state ever exposed on error, process-abort path guaranteed for relevant configuration. Lock poisoning is never sufficient soundness protection. **Evidence:** every potential panic including safe trait/user code, state at unwind/drop/reentry, initialized prefix and exact cleanup behavior. **Pair:** violation set_len to final size before cloning elements with arbitrary Clone; passing publish each initialized element only after successful write, or keep length unpublished with intentional leak-safe cleanup policy. Report resource leaks separately from uninitialized-drop UB.

### M14 — Soundness relies on safe trait law or Drop always happening (S/P0)

**Trigger:** unsafe memory indexing/ownership depends on arbitrary safe Ord/Clone/iterator behavior or on destruction of a leakable guard. **Why:** safe trait violations can cause logic errors but unsafe code must not turn them into UB; mem::forget and cycles are allowed in safe Rust. [Nomicon asymmetric trust](https://doc.rust-lang.org/nomicon/safe-unsafe-meaning.html), [leak amplification/guards](https://doc.rust-lang.org/nomicon/leaking.html), [Clone logic-error contract](https://doc.rust-lang.org/std/clone/trait.Clone.html#clone-and-partialeqeq).

**Exceptions:** specifically chosen trusted implementation, actual unsafe trait contract, API structure remains memory-safe if guard is forgotten, intentional leaking without invalid memory access. Do not call modern `std::thread::scope` unsound based on Nomicon's historical removed JoinGuard example. **Evidence:** generic/open client boundary, safe method sequence or forgotten-guard counterexample, distinction between logic and memory invariants. **Pair:** violation custom drain leaves container length covering moved-out elements until Drop, then safe client forgets drain and uses container; passing set container to leak-safe valid state before yielding guard and repair normally on Drop.

### M15 — Raw pointer/slice lifetime, provenance, extent, or alignment not upheld (S/P0)

**Trigger:** raw pointer converted to reference/slice or dereferenced after owner drop/reallocation; unbounded lifetime; null zero-length slice; adjacent allocations merged; byte length used as element count; wrong bounds/alignment/aliasing. **Why:** requirements are operation-specific and reference creation itself can be UB even without later dereference. [from_raw_parts Safety and lifetime caveat](https://doc.rust-lang.org/std/slice/fn.from_raw_parts.html), [ptr safety/provenance](https://doc.rust-lang.org/std/ptr/index.html), [Vec::as_ptr](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.as_ptr).

**Exceptions:** correctly bounded borrow tied to host owner, non-null aligned ZST/empty pointer, read_unaligned where permitted, FFI explicit null/empty normalization, raw sentinels never accessed. An integer-pointer roundtrip is not automatically UB: strict and exposed provenance APIs differ, and MMIO/FFI context matters. **Evidence:** originating allocation and lifetime, all reallocation/mutation paths, size arithmetic and isize bound, alignment, reference aliasing, specific pointer API contract; no guessed global aliasing model. **Pairs:** violation safe raw-slice method returns unconstrained `'static` reference into self, passing output lifetime tied to `&self`; violation `(null,0)` directly passed to from_raw_parts, passing permitted empty branch returning `&[]`; violation join adjacent separately allocated slices, passing owned concatenation or single-allocation subslices. **Overlap:** [cast_ptr_alignment](https://rust-lang.github.io/rust-clippy/master/index.html#cast_ptr_alignment) is deliberately overzealous; cast alone does not prove UB. Lifetime annotations do not extend allocation lifetime.

### M16 — Shared mutation violates reference uniqueness or synchronization (S/P0)

**Trigger:** mutate through shared reference outside UnsafeCell; repeated safe mutable access to same cell returns overlapping &mut; unsynchronized concurrent mutation via UnsafeCell. **Why:** UnsafeCell opts out of shared immutability, not mutable-reference uniqueness or data-race rules. [UnsafeCell aliasing](https://doc.rust-lang.org/std/cell/struct.UnsafeCell.html#aliasing-rules), [Reference UB](https://doc.rust-lang.org/reference/behavior-considered-undefined.html).

**Exceptions:** disjoint allocator/arena outputs, runtime guards that enforce exclusive access, valid atomics/synchronization, accesses proven nonoverlapping. **Evidence:** actual memory range identity, safe access API, guard enforcement, threading and reference lifetime. **Pair:** violation safe `get(&self)->&mut T` directly from UnsafeCell can be called twice; passing mutable `&mut self` accessor or borrow guard preventing a second mutable borrow. **Overlap:** [mut_from_ref](https://rust-lang.github.io/rust-clippy/master/index.html#mut_from_ref) already detects common shape and documents arena exceptions; deduplicate syntax finding, retain contextual hidden aliasing cases.

### M17 — Publication or use of incompletely initialized/invalid value (S/P0)

**Trigger:** assume_init/zeroed/transmute/reference formation/Vec::set_len publishes bytes not proved initialized and valid for actual T; assignment drops uninitialized old contents; unchecked foreign output trusted on failure. **Why:** initialized integer bytes, valid bool/enum/reference values, type-specific library invariants, and initialized container prefix are distinct requirements. [MaybeUninit initialization invariant](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html#initialization-invariant), [Vec::set_len](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.set_len), [Reference invalid values](https://doc.rust-lang.org/reference/behavior-considered-undefined.html#invalid-values).

**Exceptions:** raw MaybeUninit storage until successful writes; padding need not be initialized to produce a valid T; safe initialized-value APIs; valid zero for specifically supported types. ManuallyDrop is not uninitialized storage. **Evidence:** every field/element write, success/failure paths, actual T validity and foreign write count, initialized prefix and destructor access. **Pair:** violation FFI writes only on success but wrapper calls assume_init on every status; passing check success before assume_init. Another pair: violation Vec capacity alone followed by set_len(n); passing initialize spare capacity then set_len exact initialized count. Memory leak on partial MaybeUninit initialization may be a resource bug but is not itself UB.

### M18 — Allocation ownership/deallocation layout mismatch (S/P0)

**Trigger:** reconstruct Vec/Box/CString from foreign or incompatible raw storage, double-retake ownership, change pointee type without preserving deallocation layout, or C frees a Rust-owned CString. **Why:** ownership provenance and matching allocator/layout are required, not just pointer alignment for reads. [Vec::from_raw_parts](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.from_raw_parts), [CString::from_raw](https://doc.rust-lang.org/std/ffi/struct.CString.html#method.from_raw), [CString::into_raw](https://doc.rust-lang.org/std/ffi/struct.CString.html#method.into_raw).

**Exceptions:** correct same-allocator allocation satisfying precise reconstruction contract; matching allocator-aware API; borrowing foreign CStr/slice without claiming ownership; custom wrapper freeing through foreign API. **Evidence:** original allocation and exact size/alignment/capacity, transfer contract, single owner/reclamation, foreign mutations and allocator configuration. **Pair:** violation Vec<u16> storage reinterpreted into owning Vec<u8> and dropped, passing borrowed byte view subject to byte-validity rules or explicit newly allocated conversion; violation CString::from_raw on C malloc output, passing foreign-owner wrapper with matching foreign free and bounded borrowed view. CString from_raw must recover original length, so C must not insert/remove terminator before reclamation.

### M19 — Manual destruction exposes dropped fields (S/P0)

**Trigger:** safe lifecycle method manually drops ManuallyDrop field then returns usable object with derived/custom Debug/Clone/comparison/access that reads that field, or manual cleanup double-drops. **Why:** ManuallyDrop preserves T's validity/layout and permits safe access; dropped contents must not be exposed through public safe APIs. [ManuallyDrop hazards](https://doc.rust-lang.org/std/mem/struct.ManuallyDrop.html#safety-hazards-when-storing-manuallydrop-in-a-struct-or-an-enum).

**Exceptions:** ordinary Option::take consumes valid value and tracks state; correctly guarded custom impls/union storage; proper once-only destruction. **Evidence:** all public methods and derive-generated access, state transitions, unwind paths, MSRV/toolchain. **Pair:** violation `close()` ManuallyDrop<String> then derived Debug reads it; passing Option<String>::take or manual Debug excluding nonlive value. Version caveat: current live docs explicitly say moving a dropped ManuallyDrop containing Box was considered UB **before 1.96**, rather than presenting that historical restriction as timeless. Do not reuse stale historical rule text.

### M20 — Layout/ABI/transmute assumption is stronger than guarantees (S/P0)

**Trigger:** byte casting, FFI declaration, serialization, or transmute assumes default field order, Vec/String internal field order, arbitrary niche layout, DST pointer size, C enum validity, or that equal size implies ABI/validity compatibility. **Why:** Rust layout can vary between compilations; repr(C) does not recursively change inner field representation; UnsafeCell/MaybeUninit can remove niche optimizations of enclosing types. [Reference type layout](https://doc.rust-lang.org/reference/type-layout.html), [Vec layout guarantees](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees), [UnsafeCell layout](https://doc.rust-lang.org/std/cell/struct.UnsafeCell.html#memory-layout), [MaybeUninit layout](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html#layout-1).

**Exceptions:** specifically documented stable representation and valid values; explicit per-field encoding with endian specification; documented nullable function pointer/Option guarantees; target-specific contracts intentionally limited to that target. repr(C) does not make arbitrary String/Vec/trait object fields FFI-safe. **Evidence:** representation of every nested type, target C header/ABI, validity, padding exposure and size/alignment—not only size assertion. **Pair:** violation transmute repr(Rust) struct into assumed wire bytes; passing explicit field encoding. Another: violation transmute Option<NonNull<u8>> into Option<UnsafeCell<NonNull<u8>>> because inner layouts match; passing rebuild option through valid constructors. **Overlap:** FFI/compiler lints detect some signatures; contextual nested layout/data-dependent enum validity remains specialist review.

### M21 — FFI retained pointer/callback outlives or races owner (S/P0)

**Trigger:** foreign library stores pointer into temporary CString/Vec/stack object; asynchronous callback remains registered after target destruction; deregistration does not wait for already executing callbacks; safe wrapper permits mutation/reallocation while foreign access remains. **Why:** foreign function declarations cannot be checked against real headers by rustc; asynchronous callbacks need synchronization and no access after destruction. [Nomicon FFI calling contracts](https://doc.rust-lang.org/nomicon/ffi.html#calling-foreign-functions), [asynchronous callbacks](https://doc.rust-lang.org/nomicon/ffi.html#asynchronous-callbacks), [CString ownership docs](https://doc.rust-lang.org/std/ffi/struct.CString.html).

**Exceptions:** synchronous borrow-only call, foreign copy of data, explicit retained owner/registration object, deregistration contract ensures quiescence, properly synchronized stable storage. Drop-based deregistration is not automatically sufficient if safe clients can forget a guard and then free separately owned target memory (M14). **Evidence:** foreign API contract/version and implementation/header, copy versus retention, callback threads and reentrancy, in-flight quiescence, stable address and ownership even on errors. **Pair:** violation safe register callback points to caller stack value with no lifetime/ownership enforcement; passing registration owns stable target and documented unregister waits for callbacks before owner release. Missing foreign contract should be reported as missing evidence, not guessed away.

### M22 — FFI unwind policy mismatches both runtimes (S/P0 or C/P1 for unwanted safe abort)

**Trigger:** foreign exception enters via non-unwind ABI; Rust panic crosses callback boundary with incompatible host policy; wrapper treats catch_unwind as arbitrary foreign-exception recovery; longjmp skips Rust-owned frame destructors. **Why:** ABI and language runtime unwind rules matter. [Reference FFI unwinding](https://doc.rust-lang.org/reference/panic.html#unwinding-across-ffi-boundaries), [Reference runtime assumptions](https://doc.rust-lang.org/reference/behavior-considered-undefined.html), [Nomicon FFI unwind](https://doc.rust-lang.org/nomicon/ffi.html#ffi-and-unwinding).

**Exceptions:** correct unwind-compatible ABI and host frames; boundary contains Rust unwind and maps according to actual API contract; intentional abort policy; foreign shim handles its own exceptions. `panic=abort` is not catchable by catch_unwind. Rust panic at non-unwind boundary safely aborts; do not incorrectly label that path UB. **Evidence:** imported/exported direction, all intervening function pointers/frames, panic settings, foreign compiler exception support, runtime identity, payload handling and cleanup. **Pair:** violation C++ throw propagates through imported `extern "C"`; passing foreign shim catches/translates to error or intentional supported `C-unwind` interface. Another pair: callback host requires recoverable status but Rust panic aborts at extern C boundary; passing contain recoverable Rust panics with a correctly designed boundary/error policy. **Source discrepancy:** current Reference gives catching foreign unwind by catch_unwind/join an **unspecified choice of abort or Err with opaque payload**, while Nomicon still calls catch_unwind interaction undefined. Prefer current Reference/std guarantees and do not advertise foreign recovery as reliable; record the discrepancy rather than flattening them into one timeless statement. `C-unwind` also does not make `-fno-exceptions` host frames safe.

### M23 — Manual Send/Sync implementation exceeds actual guarantees (S/P0)

**Trigger:** unsafe impl lacks necessary generic bounds or makes thread-affine foreign object/single-threaded refcount/interior mutation shareable without enforcing synchronization/ownership. **Why:** Send and Sync are unsafe contracts, not permission toggles. [Nomicon Send/Sync](https://doc.rust-lang.org/nomicon/send-and-sync.html), [Arc thread safety](https://doc.rust-lang.org/std/sync/struct.Arc.html#thread-safety).

**Exceptions:** custom unique owner with correct bounds and allocator/drop cross-thread guarantees, synchronization allowing weaker/different bounds than naive field matching, opaque handle explicitly documented thread-safe. Do not require T:Send+Sync indiscriminately for both traits: correct bounds depend on access and ownership. **Evidence:** safe methods/traits exposing T, all mutation, foreign thread affinity and destructor execution, raw pointer ownership, necessary bounds. **Pair:** violation unique owning raw-pointer Box-like wrapper declares Send for every T allowing Rc payload crossing threads; passing Send when T:Send and Sync when T:Sync under the wrapper's demonstrated semantics. **Overlap:** concurrency/security domain.

### M24 — Pinning abstraction permits moving/invalidation of address-sensitive state (S/P0)

**Trigger:** unsafe Pin creation/projection/unchecked mutable access, custom pinning pointer Deref/Drop, structural projection or manual Unpin allows a previously pinned !Unpin state to move or invalidate its storage before necessary destruction. **Why:** Pin is a library contract, not compiler magic, and pins the pointee, not pointer handle. [std::pin source-of-truth](https://doc.rust-lang.org/std/pin/index.html), [structural pinning](https://doc.rust-lang.org/std/pin/index.html#projections-and-structural-pinning), [Drop guarantee](https://doc.rust-lang.org/std/pin/index.html#subtle-details-and-the-drop-guarantee).

**Exceptions:** T:Unpin, fields deliberately nonstructural with no dependent invariant, valid Pin::set (drops old value first), safe pin!/Box::pin use with correct abstractions, leaking permanently retained pinned storage (not deallocating/reusing it). Moving Pin<Box<T>> handle does not itself move T. Box alone does not enforce pinning. **Evidence:** lifecycle/address-sensitive state, actual Unpin impl/auto traits, every field projection/accessor, Drop/reuse behavior, panic cleanup, pointer Deref contracts. **Pair:** violation wrapper projects Pin<&mut T> but also offers take() moving that structural T, or unconditionally implements Unpin for generic structural field; passing enforce structural bounds and prohibit move-out. Another: violation Drop mem::replace moves pinned field; passing pinned destruction without moving it. Packed structurally pinned types require special rejection: std docs say repr(packed) drop may move fields. Do not mandate Pin for ordinary borrowed/owned data or all async code; use established projection support where already available, not a new abstraction to satisfy style. Current docs include experimental pin-related APIs; do not prescribe nightly `Drop::pin_drop` as baseline.

### M25 — Secret erasure incorrectly assumes ordinary drop/clear/zeroing suffices (C/P1 when erasure is required)

**Trigger:** security requirement promises key/secret erasure but implementation relies on Vec::clear/drop or ordinary zeroing that may be optimized away. **Why:** Vec explicitly does not erase removed data and warns that even zeroing may be removed by optimization. [Vec security caveat](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees).

**Exceptions:** no erasure guarantee or threat requirement; already selected erasure mechanism with its own documented limits. Source establishes failure of naive assumption, not a proof that any particular dependency erases all copies. **Evidence:** actual security/retention requirement, buffer ownership and clones, optimizer-resistant erasure API's documentation, temporary copies and swap/platform limitations. **Pair:** violation key Drop just clear() with explicit erasure guarantee; passing use existing documented erasure facility within its scope and avoid unnecessary secret copies. **Overlap:** security domain; exclude generic “all buffers must zeroize” mandate.

### M26 — Conflicting atomic/non-atomic or mixed-size accesses (S/P0)

**Trigger:** unsafe raw memory access overlaps an atomic operation without a happens-before relationship and at least one conflicting access writes; or nonsynchronized conflicting atomics partially overlap with different access sizes. **Why:** std defines data races and mixed-size atomic access restrictions. Rust uses an access-based translation of C++20's model; do not transplant C++ object partitioning literally. [Atomic access memory model and paired examples](https://doc.rust-lang.org/std/sync/atomic/index.html#memory-model-for-atomic-accesses).

**Exceptions:** concurrent atomic and non-atomic reads with no modification are expressly permitted; join/other valid synchronization orders conflicting accesses; disjoint atomic regions; exact same region and size for supported atomic operations. A failed compare_exchange is not a write. **Evidence:** exact overlapping byte ranges/access sizes, atomic/non-atomic operations, at least one write, synchronization/happens-before graph and target alignment/atomic support. **Pair:** violation AtomicU16 store races with unsafe `.as_ptr().write(...)`; passing join establishes happens-before before the non-atomic write. Another pair: violation AtomicU16 and overlapping AtomicU8 stores in parallel; passing synchronization or disjoint storage. **Overlap:** concurrency research owns publication ordering/read-from semantics; memory slice owns this specific unsafe access-soundness obligation. Do not report all Relaxed use or all mixed read access as unsound.

## Tool-owned inventory and deduplication

1. **rustc borrow/lifetime/type/auto-trait checks:** multiple incompatible safe borrows, use after move, ordinary dangling borrowed returns, invalid Drop/Copy combination, Send/Sync bounds, direct Drop::drop calls, obvious packed-reference violations. [Book borrow rules](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html), [Drop](https://doc.rust-lang.org/std/ops/trait.Drop.html). Compiling safely does not establish business correctness or correctness of unsafe internals.
2. **rustc unsafe syntax lint:** [unsafe_op_in_unsafe_fn](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html) warns by default in edition 2024. It separates unsafe body operation from caller contract; it does not verify the latter. Do not reinterpret adding unsafe braces as solving a safety bug.
3. **Clippy documented candidates:** [clone_on_copy](https://rust-lang.github.io/rust-clippy/master/index.html#clone_on_copy), [boxed_local](https://rust-lang.github.io/rust-clippy/master/index.html#boxed_local), [arc_with_non_send_sync](https://rust-lang.github.io/rust-clippy/master/index.html#arc_with_non_send_sync), [missing_safety_doc](https://rust-lang.github.io/rust-clippy/master/index.html#missing_safety_doc), [mut_from_ref](https://rust-lang.github.io/rust-clippy/master/index.html#mut_from_ref), [cast_ptr_alignment](https://rust-lang.github.io/rust-clippy/master/index.html#cast_ptr_alignment), [mem_forget](https://rust-lang.github.io/rust-clippy/master/index.html#mem_forget), [forget_non_drop](https://rust-lang.github.io/rust-clippy/master/index.html#forget_non_drop), [manual_dangling_ptr](https://rust-lang.github.io/rust-clippy/master/index.html#manual_dangling_ptr), [await_holding_lock](https://rust-lang.github.io/rust-clippy/master/index.html#await_holding_lock), [await_holding_refcell_ref](https://rust-lang.github.io/rust-clippy/master/index.html#await_holding_refcell_ref). These are catalog examples, not a recommendation to deny every one. In particular mem_forget is an allow-by-default restriction lint, cast_ptr_alignment allows legal aligned/unaligned patterns, mut_from_ref notes disjoint allocator outputs, and await-holding lints document explicit-drop false positives.
4. **Toolchain-specific catalog validation required:** names/default levels and Clippy coverage change. Check the project's pinned release before selecting settings. [Clippy usage](https://doc.rust-lang.org/clippy/usage.html) explicitly discourages enabling all restriction lints and describes pedantic opinion/intentional false positives. Do not promote every catalog item into a universal norm.
5. **rustfmt:** formatting only; not ownership, lifetime, cleanup or soundness review.

Deduplicate by underlying root obligation. Example: uninitialized set_len before Clone belongs to M13, with M17 as supporting invariant, not two separate errors. A forgotten drain's UB belongs to M14 and M12; a benign strong cycle belongs to M06, not M14. The async/concurrency slice should own guard-across-await syntax and runtime-specific cancellation; memory slice supplies resource/state invariants. FFI signatures/layout overlap M20/M22; preserve one specific root report with enough context.

## Testing/review mechanisms: what they can and cannot establish

| Mechanism | Useful evidence | Limitations / reporting rule |
|---|---|---|
| rustc + configured Clippy | Static borrow/type/lint diagnostics in selected targets/features | Unsafe contracts and many logic/resource properties remain unchecked; Clippy advice can be conditional. Do not claim all configurations checked. |
| Miri | Executed UB such as use-after-free, invalid initialization/alignment, intrinsic preconditions, data races; some weak-memory behavior; leak detection | [Official Miri README](https://github.com/rust-lang/miri): one particular execution/input is not all safe clients; unspecified layouts may pass; most FFI/platform APIs unsupported; seeds vary schedules but not exhaustively. Unsupported operation is not a code bug. Stacked Borrows and optional Tree Borrows are explicitly experimental; Miri's approximation is not a final Rust specification. |
| Sanitizers | Instrumented native runtime evidence for address/free/leak/uninitialized-read/data-race bugs according to chosen sanitizer | [rustc sanitizer docs](https://doc.rust-lang.org/unstable-book/compiler-flags/sanitizer.html): unstable configuration, target support/runtime overhead, appropriate instrumentation and cross-language setup needed; absence of failure is not soundness proof. Native FFI coverage may complement Miri, but uninstrumented foreign code can hide bugs. ASan/TSan are not Rust lifetime/aliasing proofs. |
| Loom | Explicitly modeled thread/synchronization execution counterexamples and small modeled invariant tests | [Official loom docs](https://docs.rs/loom/latest/loom/): only Loom-replaced operations are visible, external nondeterminism must be modeled, preemption bounds prune coverage, state/thread limits and relaxed-memory reorderings mean it is not a whole-program proof. Distinguish modeled schedules from all real executions. |
| Human/LLM semantic review | Map API contracts to actual paths; find missing bounds, owner retention, resource cycles, callback lifetimes, panic cleanup; propose counterexample fixture | Plausible judgment only. No universal soundness certificate; cite actual supporting contracts and mark missing context/inference. Escalate contentious aliasing/provenance questions rather than invent rules. |

Fixture acceptance should include a negative and positive near-neighbor plus legitimate-exception cases. Specialist negative fixtures must be clearly designated unsafe counterexamples and not executed as ordinary production examples. Important exceptions: Arc clone intentionally shares; arena returns disjoint &mut; Vec capacity reuse; destructor leakage remains memory-safe; Unpin/nonstructural pin field; null-to-empty FFI handling; non-unwind Rust panic intentionally aborts; foreign allocation freed with its foreign API. No verification was performed here.

## Version and authority caveats

- Live `doc.rust-lang.org` pages can advance beyond project MSRV and mix stable/experimental entries. Record supported edition/toolchain and use pinned-release contracts for proposed fixtures/policies. Notably current ManuallyDrop docs explicitly revise the historical Box move restriction; current Drop docs include nightly pin_drop.
- Reference says unsafe aliasing rules are not completely determined and its UB list is not exhaustive. Do not turn Stacked/Tree Borrows or disputed union/raw-vtable validity into unquestioned universal rules. Prefer uncontested operation-specific std preconditions for default candidates.
- FFI behavior requires the actual foreign contract, target ABI, allocator, headers, exception support, and runtime identity. Repr(C), non-null pointers, or a matching size test alone do not establish a correct binding.
- Prefer current Reference/std when older Nomicon prose conflicts; preserve the foreign catch_unwind discrepancy above. Nomicon pedagogical/historical examples are not current API implementation guarantees.

## What NOT to include in the semantic pack

- Reimplemented compiler borrow/lifetime errors, formatting rules, exact missing `# Safety` section checks, or Clippy-covered token/shape checks without contextual added value.
- Blanket bans on clone, allocation, Box, Arc/Rc, RefCell, Mutex, unsafe, raw pointers, traits, dyn dispatch, unwrap/expect, mem::forget, ManuallyDrop, or explicit lifetimes.
- Universal function/borrow/lock/allocation size limits, clone-count quotas, always-with_capacity/always-shrink_to_fit/always-zeroize rules, or mandatory deep copies. No ecosystem source establishes these universal policies.
- Mandatory `Arc::clone(&x)` rather than `x.clone()`: Arc docs explicitly describe both syntaxes and personal preferences. Likewise, universal Rc over Arc ignores documented library flexibility.
- Rules treating `'static` as proof of immortal resources, lifetime annotations as extending allocation lifetime, Arc as making its payload thread-safe, UnsafeCell as permitting aliased &mut/data races, ManuallyDrop as permitting invalid values, or Pin as pinning its pointer handle/all fields automatically.
- Rules concluding safety from a `SAFETY:` comment, missing documentation as proof of UB, compiling safe wrapper as soundness proof, or a clean Miri/sanitizer/Loom run as all-client/all-platform correctness.
- Automatic replacement of every async std mutex with Tokio mutex. [Tokio's own Mutex docs](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html) often prefer ordinary mutex for plain data when not held across await; async guards can legitimately cross await.
- A frozen universal unsafe aliasing model, arbitrary rejection of raw-pointer casts/sentinels, or unsupported claims that layout observed on one target is stable wire/ABI layout.
- Historical removed APIs presented as current defects, nightly pin APIs imposed on stable projects, blanket `C-unwind` edits, or claims that catch_unwind catches abort/foreign exceptions reliably.
- Business transactional consistency labeled memory UB without evidence, resource leakage universally forbidden despite legal intentional process-lifetime/leak-safe designs, or retries/fallbacks introduced to suppress genuine invariant failures.
