# Rust pack research: API, function structure, errors, documentation, compatibility

Original research phase (before implementation): research/proposal only. Primary sources below were read live; no repository implementation, provider calls, installs, builds, tests, or formatting were performed during that phase. Fixture descriptions are proposed future fixtures, not executed test results.

## Evidence strength and scope

- **Language/tool contract:** Reference rules and std trait contracts are authoritative for the particular feature/trait; a compiler may enforce only part of a semantic contract.
- **Official ecosystem recommendation:** Rust API Guidelines are explicitly a set of recommendations, primarily for reusable library APIs, not a language mandate. The Book teaches accepted approaches and also explicitly permits exceptions.
- **Conditional judgment:** A rule below applies only when its trigger and context establish the relevant problem. It must identify concrete harm, not merely request the author's preferred abstraction.
- **Project policy:** MSRV, panic strategy, public stability promises, target platforms and application interface promises must be read from the project. Do not invent them.
- Library public APIs deserve stronger interoperability/documentation/evolution scrutiny than private helpers. Binaries retain discretion over fatal initialization, error rendering and application compatibility. `no_std` is not synonymous with no allocation: `alloc` can be brought in separately. `core::error::Error` is available from Rust 1.81; older MSRVs require different handling. Do not demand `std`, heap-allocated errors, threading support or extra crates in all environments.

## Candidate semantic inventory

These are proposed Jev judgments. Diagnostic wording should describe the observed defect and preserve the listed exceptions. “Failing” means violating the proposed rule, not necessarily failing to compile.

### API01 — Preserve caller choice for expected failure (high priority)
- **Trigger/why:** A library/parser or application boundary panics (`unwrap`, `expect`, indexing, explicit panic) on ordinary malformed input, I/O failure or network failure. Returning/handling `Result` is the Book's good default; making expected failure unrecoverable removes caller choice. Sources S1, S13.
- **Exceptions/context:** Tests, prototypes, illustrative snippets; proven invariants; documented programmer-error contracts; application-owned fatal startup policy. Determine input provenance, possible failure, library vs binary, documented promises and error handling above the call. `unwrap` alone is not a finding.
- **Fixtures:** Fail: public config parser calls `user_text.parse::<u16>().unwrap()`. Pass: returns parse error; invariant parse of literal `127.0.0.1` with a justified `expect`; test setup unwrap; CLI explicitly reports fatal startup error and exits according to its policy.
- **Dedup:** Prefer compiler unused-result and configured panic lints for syntax; Jev owns expected-vs-invariant reasoning. Consolidate with API02 if both describe the same operation.

### API02 — Explain genuine invariant-based panic assumptions (high priority)
- **Trigger/why:** A nontrivial production `expect` claims success without identifying the invariant that makes failure unexpected, or its assumption is contradicted by the data flow. std recommends describing why the result *should* be `Ok`; the Book accepts reasoning unavailable to the compiler. Sources S1, S2.
- **Exceptions/context:** Obvious local invariant, tests, deliberate application fatality; do not require the literal word “should”, an extra comment at every unwrap, or replacing every unwrap with expect. Need dominating checks, transformations, mutability and failure semantics.
- **Fixtures:** Fail: `config.parse().expect("failed")` justified as infallible despite user input. Pass: parsing known valid literal with `expect("hardcoded IP address should be valid")`; proof supplied by local control flow.
- **Dedup:** API01 wins when failure is ordinary; this candidate is mainly informative for valid but unclear invariant reasoning.

### API03 — Preserve useful error causes and boundary context (high priority)
- **Trigger/why:** A higher-level error wrapper discards a lower-level cause (`map_err(|_| GenericError)`) although callers/debuggers need it, or many indistinguishable operations return errors without identifying the relevant resource/operation. std explicitly supports source chains at abstraction boundaries; its example carries a config path. Sources S2, S3, S13. Context completeness is a conditional recommendation, not a mandate to add context to every `?`.
- **Exceptions/context:** Intentional security redaction; public abstraction that deliberately hides internals; boolean-like domain rejection with no useful cause; lower error already sufficiently identifies the operation. Never require secrets in messages. Need caller recovery, logging/rendering path, existing cause, privacy and boundary semantics.
- **Fixtures:** Fail: config reader maps every I/O error to “invalid config”, losing permission/not-found distinctions and path. Pass: typed wrapper retains path + `source`; intentionally sanitized public response retains diagnostic internally.
- **Dedup:** Do not also report API04 merely because API03 discarded information. No compulsory `anyhow`, `thiserror`, `eyre`, `miette` or manual implementation style.

### API04 — Public error interfaces interoperate when applicable
- **Trigger/why:** Public `Result` error has no meaningful identity/diagnostic (`()`, opaque integer codes without documented meaning) or unnecessarily lacks `Error`/`Display`/`Debug`, blocking error composition. API Guidelines recommend meaningful errors and thread-friendly `Send + Sync`; Sources S2.
- **Exceptions/context:** Internal signaling; intentional lightweight status protocol; `no_std` MSRV before `core::error::Error` stabilized; intentionally thread-local error resources. `'static`, `Send` and `Sync` are useful conditional capabilities, not mandatory bounds on every application/internal error. Need exported reachability, runtime/thread use, MSRV and targets.
- **Fixtures:** Fail: exported `parse` returns `Result<Record, ()>` with distinct actionable failures. Pass: named `ParseError` with formatting and `Error`, preserving cause where applicable; old-MSRV core-only crate with documented portable error type.
- **Dedup:** Tool checks should own mechanically detectable unit error or missing implementations; Jev only assesses meaning/context.

### API05 — Standard conversions obey their semantic contract (high priority)
- **Trigger/why:** `From` panics on invalid source values or silently changes/discards semantically relevant information; standard From expectations are infallible, lossless, value-preserving and obvious. Sources S3. Use `TryFrom` for fallible conversion or an explicitly named operation for non-obvious conversion.
- **Exceptions/context:** Semantically irrelevant capacity/layout information can be lost; allocation failures are not a blanket reason to reject standard allocating conversions. Need all accepted values and domain meaning. Direct Into implementation has a historical pre-1.41 foreign-target exception; function bounds may appropriately use Into.
- **Fixtures:** Fail: `From<u32> for Port` narrowing via `as u16`; `From<&str>` parsing arbitrary input then unwrap. Pass: `TryFrom<u32>` validates range; wrapping `Ipv6Addr` into a variant; named `truncate` for explicit truncation.
- **Dedup:** Tool owns `from_over_into` and simple panic patterns; Jev owns domain loss/value meaning.

### API06 — Keep validated type invariants enforceable (high priority)
- **Trigger/why:** A constructor validates a claimed domain invariant but public fields, mutable accessors, conversions or deserialization paths bypass it; downstream functions then assume valid values. Prefer static enforcement and boundary checks when practical. Sources S1, S4, S5, S10.
- **Exceptions/context:** Passive DTOs; temporary unchecked state before a documented validation step; unsafe opt-out with explicit caller obligations; an existing std type already encodes the invariant. Expensive debug assertions cannot protect a required safety/trust-boundary check in release. Need complete constructors/accessors/impls, serialization/FFI and consumer assumptions.
- **Fixtures:** Fail: `Percentage::new` accepts 0..=100 but field is `pub u8` and methods rely on <=100. Pass: private field + fallible validated construction; `NonZeroUsize` instead of another bespoke wrapper.
- **Dedup:** Consolidate field-privacy and validation diagnostics into this root cause. Ownership/memory slice may cover unsafe implications.

### API07 — Use domain types where ambiguity produces actual misuse
- **Trigger/why:** Same primitive parameters represent noninterchangeable units/IDs, opaque boolean modes or a state tag plus contradictory optional payloads; call sites can easily swap them or construct invalid combinations. Guidelines recommend newtypes/custom types; Book explains enum-associated payloads. Sources S5.
- **Exceptions/context:** `bool` naturally represents truth/enabled state; `Option<T>` naturally represents absence; simple local tuple computations; FFI/wire layout; no demonstrated ambiguity. Do not wrap every primitive or force typestate. Need callsites, invariant, domain distinctions and construction cost.
- **Fixtures:** Fail: `transfer(user_id: u64, order_id: u64)` with mixed callers; `State { kind: Ready, error: Some(...), value: None }`. Pass: `UserId`/`OrderId`; `State::Ready(Value)` / `State::Failed(Error)`; `set_enabled(bool)` remains valid.
- **Dedup:** Compiler can prevent misuse after types exist, but choosing a justified type is semantic. Keep separate from function arity metrics.

### API08 — API ownership leaves copying/placement with caller
- **Trigger/why:** Function requires ownership but takes borrow then unconditionally clones, or unnecessarily consumes a non-Copy value only to inspect and discard it. Guidelines explicitly prefer caller control. Sources S6.
- **Exceptions/context:** Clone preserves abstraction/invariants; API intentionally snapshots; cheap Copy values; ownership communicates lifecycle completion; already-public signature has compatibility cost. Need actual ownership uses and all callers; do not ban clone or require borrow when storage/async/task lifetimes need ownership.
- **Fixtures:** Fail: `Store::insert(&String)` unconditionally clones into owned storage while callers have an owned String; `count(String)` only examines it. Pass: accepts owned String for storing; `count(&str)`; explicit snapshot clone where the original must remain reusable.
- **Dedup:** High overlap with memory slice and tool needless-pass/ptr-arg checks. One owner; do not repeat local clone-count warnings.

### API09 — Prefer methods when there really is a clear receiver
- **Trigger/why:** Public free function acts solely on a type owned by the crate, hiding an ordinary discoverable operation outside its API. Guideline C-METHOD supports receiver methods/autoborrowing/rustdoc discoverability. Source S7.
- **Exceptions/context:** Symmetric operations with no clear receiver; types owned by another crate; extension traits justified by ownership; FFI entry points; generic algorithms. Need type ownership, callers and interface role. Do not force a trait just to turn one function into a method.
- **Fixtures:** Fail: `pub fn balance(account: &Account)` scattered outside owned Account API without another role. Pass: `Account::balance(&self)`; `distance(a, b)` free function when neither is privileged.
- **Dedup:** Low-priority API review, not a blanket style failure.

### API10 — Return new results; reserve mutation parameters for intentional reuse
- **Trigger/why:** Public function uses `&mut` out-parameters only to assign fresh computed outputs. Guideline prefers tuple/struct returns, which need no heap allocation. Source S7.
- **Exceptions/context:** Reuse caller buffers, in-place algorithms, streaming I/O, FFI, APIs intentionally modify existing state. Need mutation purpose and allocation/reuse contract.
- **Fixtures:** Fail: `bounds(input, &mut min, &mut max)` solely writes newly computed scalars. Pass: `bounds(input) -> Bounds`; `Read::read(&mut [u8])` buffer reuse.
- **Dedup:** Do not diagnose all mutable arguments, and do not propose allocation-heavy returns for reused buffers.

### API11 — Generalize inputs only to capabilities the function needs
- **Trigger/why:** Reusable API unnecessarily demands one owned/concrete container when it only iterates or borrows, causing callers to materialize/copy data. C-GENERIC advises minimizing assumptions; costs include code size/signature verbosity. Source S6.
- **Exceptions/context:** Random access/slice layout required; performance/code-size constraints; private helper; simple `&[T]` is often perfectly suitable; domain-specific concrete type encodes invariants. Need implementation operations and real callers. Not “make every function generic.”
- **Fixtures:** Fail: `sum(&Vec<i64>)` rejects available slice callers while only using slice operations. Pass: `sum(&[i64])`; `sum<I: IntoIterator<Item=i64>>(I)` when iterator sources are a real requirement; concrete Vec when capacity/mutation is essential.
- **Dedup:** ptr-arg/tool checks first. Generic broadening can itself change inference/compatibility; review API21 before suggesting it.

### API12 — Preserve intended dyn usability; do not mandate dispatch style
- **Trigger/why:** Trait documented for runtime polymorphism gains required generic/Self-returning methods making it dyn-incompatible, or an API falsely promises heterogeneous implementations while constraining all values to a single generic T. Guidelines require deciding the intended use, not universal dyn compatibility. Sources S6, S11.
- **Exceptions/context:** Trait intentionally static-only; concrete closed-world enum dispatch; `where Self: Sized` methods intentionally unavailable via dyn; code-size/performance tradeoffs. Need dyn callsites, extension promises, distribution of concrete types and baseline API. `&dyn Trait` does not require heap allocation; Box ownership and dyn dispatch are distinct choices.
- **Fixtures:** Fail: plugin trait documents `Box<dyn Plugin>` support then adds unrestricted `fn configure<T>(...)`. Pass: generic helper gated `Self: Sized`, preserving object-usable methods; heterogeneous `Vec<Box<dyn Draw>>`; statically dispatched collection explicitly intended homogeneous.
- **Dedup:** rustc enforces actual dyn use; Jev should only diagnose contradictory design promises/compatibility, not uninstantiated traits solely for being dyn-incompatible.

### API13 — Avoid unnecessary definition-wide generic bounds
- **Trigger/why:** Struct definition repeats derivable bounds needed only by some impls, restricting all consumers and future evolution. C-STRUCT-BOUNDS recommends putting those bounds on applicable implementations. Source S8.
- **Exceptions/context:** Associated type use; `?Sized`; Drop requires bounds on the type; genuine invariant semantically depends on bound. Need field types, associated types, Drop and all impls.
- **Fixtures:** Fail: `#[derive(Clone, Debug)] struct Cache<T: Clone + Debug> { value: T }` when no field requirement needs bounds. Pass: `struct Cache<T>` with conditional derived implementations; `struct Reader<R: Read>` when a matching Drop bound requires it.
- **Dedup:** Deterministic bound-analysis lint/codemod may cover straightforward forms. No automatic public-bound removal without compatibility review.

### API14 — Deref is transparent pointer-like behavior, not inheritance
- **Trigger/why:** Wrapper uses Deref/DerefMut simply to inherit unrelated methods; coercion unexpectedly exposes mutable access that bypasses invariants, performs surprising work, fails unexpectedly, or commits the public API to an unintended target. Sources S7. Prefer current std nuanced criteria over a crude syntactic “only smart pointers” ban.
- **Exceptions/context:** String/Vec-style transparent smart-pointer behavior; cheap unsurprising target access; programmer-error panic can be permissible. Need target methods, coercion callsites, mutability invariants, cost and API commitment. AsRef/Borrow may be alternatives only if their own semantics fit.
- **Fixtures:** Fail: validated `Email` DerefMut to String lets callers insert invalid text; generic smart pointer methods collide with arbitrary T. Pass: cheap immutable transparent deref with intended API; explicit accessor for nontransparent domain type.
- **Dedup:** Memory slice may own invariant bypass; report once at exposing interface.

### API15 — Common traits should fit semantics, and law-related traits must agree
- **Trigger/why:** Public type cannot be compared/formatted/collected in a way the domain plainly supports, or manual equality/hash/order implementations disagree. API Guidelines recommend *applicable* common traits due to orphan rules; std defines required equality/hash consistency. Sources S8, S7.
- **Exceptions/context:** Identity/resource types may not support Clone/Copy/Ord/Default; NaN prevents Eq; sensitive Debug needs redaction; nondeterministic values may not support meaningful ordering. Trait laws are not optional but trait availability is conditional. Need domain equality and every related impl, not simply derives list.
- **Fixtures:** Fail: equality compares `id` but Hash hashes `id` and mutable label; custom Eq and derived Ord disagree on identity. Pass: coherent derives when fields define semantics; manual Hash hashes identity fields; no Copy on resource owner; redacted useful Debug.
- **Dedup:** Tool handles inconsistent derive/impl patterns if supported; Jev only reasons about the uncovered semantics. Collection FromIterator/Extend is a conditional interoperability suggestion, not compulsory for every wrapper.

### API16 — Default and empty new agree when both mean default construction
- **Trigger/why:** Public `new()` and `Default::default()` construct materially different baseline values without an established domain distinction. Guidelines explicitly expect the same behavior. Sources S7, S8.
- **Exceptions/context:** `new` takes required arguments; no meaningful default exists; alternative constructor `open/connect/bind` follows domain semantics. Do not require Default to fabricate invalid or arbitrary state.
- **Fixtures:** Fail: zero-argument `Cache::new()` uses capacity 64 and enabled mode while Default uses disabled/unusable state despite docs equating them. Pass: new delegates to default; argument-requiring new has no Default.
- **Dedup:** Mechanical missing-Default lint separate from behavioral agreement. Naming of constructors is recommendation, not universal requirement to call every constructor new.

### API17 — Document actual public error/panic/safety contracts (high priority)
- **Trigger/why:** Public docs omit or misstate recoverable failures, meaningful panic conditions, mutation on failure, or unsafe caller obligations; section headings exist but provide no usable contract. C-FAILURE expressly covers trait methods too. Source S9.
- **Exceptions/context:** Do not enumerate every conceivable panic inside caller-provided Display/closure logic; no mandatory empty Errors/Panics sections for infallible functions. Need transitive behavior, unsafe preconditions, code paths, exported reachability and trait-implementation contract.
- **Fixtures:** Fail: unsafe pointer API Safety says “be careful” but omits alignment/lifetime; checked constructor docs promise no panic but unwraps ordinary bad input. Pass: concrete Safety invariants, relevant Errors/Panics conditions, accurate partial-state contract.
- **Dedup:** rustdoc/Clippy owns missing-heading/basic documentation diagnostics; Jev assesses accuracy/completeness. Memory slice owns unsafe code correctness, this rule owns public obligations.

### API18 — Examples show useful usage and remain testable when feasible
- **Trigger/why:** Public API has no usable example/link for nonobvious behavior, examples misrepresent ownership/failure, or a normal example is marked ignore without necessity. API Guidelines explicitly apply examples “within reason”; rustdoc supports hidden setup and compiling no_run examples. Source S9.
- **Exceptions/context:** Link to related item may suffice; obvious APIs need not each repeat ceremony; external network/OS interactions justify no_run; intended invalid code uses compile_fail; educational Book snippets may unwrap whereas reusable API docs recommend `?`. Need docs purpose and test environment.
- **Fixtures:** Fail: reusable fallible config example unwraps arbitrary user data as normal production usage; ignore used solely to hide a type error. Pass: hidden `Result`-returning main + `?`; no_run for network access; compile_fail for invalid state construction; linked meaningful shared example.
- **Dedup:** rustdoc execution catches compilation/staleness; Jev checks pedagogical usefulness and unjustified suppression. Never demand execution of external side effects in docs tests.

### API19 — Expose intentional interfaces, not accidental implementation details
- **Trigger/why:** Library exports internal helpers/types/fields to cross an internal module boundary, causing downstream coupling or bypassing invariants when `pub(crate)`/private modules suffice. Guidelines treat representation as a commitment and docs as user-facing surface. Sources S9, S10.
- **Exceptions/context:** Passive public records, intentional low-level API, stable reexports, tooling macro helpers needing visibility, documented representation contracts. `#[doc(hidden)]` hides documentation, not visibility or compatibility by itself. Need downstream reachability/reexports, tests/macros, intended users and existing promises.
- **Fixtures:** Fail: public parser machinery only called internally, published merely to let sibling module invoke it. Pass: `pub(crate)` implementation helper + public domain facade; intentionally public DTO fields.
- **Dedup:** API06 owns invariant-bypass cases. Do not “fix” an existing public API by removal in a compatible release without API21.

### API20 — Seal only traits intentionally closed to downstream implementations
- **Trigger/why:** Public trait is described as crate-owned/closed-world but allows downstream impls, undermining promised evolution strategy; or sealed trait fails to explain that restriction. Guidelines support sealing *some* traits, not all. Sources S8, S11.
- **Exceptions/context:** Extension/plugin traits must remain open; generic abstraction intentionally supports user implementations; sealing later can break users. Need documented extension point and baseline implementations.
- **Fixtures:** Fail: supposedly closed indexing helper relies on adding required methods compatibly but is unsealed and implementable externally. Pass: private supertrait + documented sealing from introduction; open plugin trait remains open.
- **Dedup:** Lower-priority API design review; no universal “seal every trait” rule.

### API21 — Respect existing compatibility promises (high priority when diff/baseline exists)
- **Trigger/why:** Change removes/renames/moves exported items, expands exhaustive enums, adds required trait items, tightens bounds, removes dyn compatibility, drops no_std, or otherwise violates declared compatible-release/API promises. Cargo gives classifications, not universal hard-and-fast rules. Sources S11, S9.
- **Exceptions/context:** Intentional breaking release with clear release notes; internal unreachable items; documented unsupported interfaces; 0.y.z uses Cargo's left-most nonzero compatibility convention. Need old/new public surfaces, release/version intent, cfg/feature matrix, downstream use, API docs and changelog. From a single snapshot do not invent a previous promise or infer a breaking change.
- **Fixtures:** Fail: 1.4 -> 1.5 adds enum variant to public exhaustive enum used by downstream match; required method added to open trait. Pass: new variant on originally non_exhaustive enum; explicit major release and migration notes. Adding non_exhaustive later is itself breaking for previously exhaustive public types.
- **Dedup:** API-diff/semver tools should detect structural changes; Jev assesses release intent, behavioral/documented contracts. Application CLI/output/data compatibility depends on project commitments, not library signature rules alone. MSRV increases are Cargo's *possibly-breaking* category, generally recommended minor rather than automatic major.

### API22 — Features and optional std support compose as declared
- **Trigger/why:** Library feature disables API/capabilities another dependency expects, conflicting features break ordinary feature-union builds, or std becomes unavoidable under a claimed no_std configuration. Cargo recommends additive features and std opt-in feature, not a subtractive no_std feature. Sources S12, S11.
- **Exceptions/context:** Rare genuine incompatibilities with explicit compile_error and documented combinations; applications have different composition pressure; std allowed for tests only; no_std plus alloc is valid. Need feature graph, dependencies, supported targets, cfg branches and support promises.
- **Fixtures:** Fail: `no_std` feature removes otherwise available API when unified with another dependent's feature set; supposedly no_std path requires std Error below unsupported target. Pass: core-first crate enables optional std additions; optional alloc used knowingly; explicit unsupported mutually exclusive combination clearly documented.
- **Dedup:** Cargo/target builds prove capability; Jev evaluates feature intent, not a regex ban on std imports or extern crate (alloc explicitly needs extern crate).

### API23 — Tests assert the relevant observable behavior
- **Trigger/why:** Regression/contract test invokes changed code but never checks its result, only checks “doesn't panic” when a value/error/side effect is the actual promise, or tests a wrapper's unrelated setup rather than claimed contract. Book describes setup, exercising code and asserting expected outcome; external integration tests exercise public API. Source S13.
- **Exceptions/context:** No-panic itself can be the contract; compile-only trait/auto-trait tests; Result-returning tests fail through `?`; meaningful should_panic; doctests; externally asserted effects. Do not enforce coverage percentage, one test per function, private-only or public-only testing ideology.
- **Fixtures:** Fail: test calls parser and discards Result yet named “rejects_invalid_port”. Pass: asserts error variant; tests accepted boundary value; downstream-style integration/doctest confirms public call shape; Send/Sync compile assertions for promised threading capability.
- **Dedup:** Compiler unused-result and test linters catch basic cases; Jev checks relevance, not demand a specific framework. For hash tests compare Eq consistency, not hard-coded standard hash outputs (S8 portability).

### API24 — Separate unrelated responsibilities when they obstruct reasoning/testing
- **Trigger/why:** Function intertwines independent parsing, business computation, I/O and presentation/error handling so changes/tests of one concern require unrelated side effects or entangled state. Book explicitly advises one task per function and demonstrates slim main / testable logic separation. Source S13.
- **Exceptions/context:** Straight-line orchestration is itself one task; tiny CLI/scripts; performance-critical fusion; existing local helpers already express phases; no benefit from extra public library crate. Need actual dependencies/side effects and callers, not lines/nesting alone.
- **Fixtures:** Fail: main contains independent config validation, search algorithm, file writes and output formatting, making pure search testing require filesystem/process setup. Pass: main configures, calls run and handles error; extracted computation can be tested directly; short orchestration stays together.
- **Dedup:** This is conditional Book-backed guidance, not a numeric function-length/parameter cap. No forced function split for every match arm or repeated two-line block.

### API25 — Builders/configuration types only solve actual construction complexity
- **Trigger/why:** Public type has many interacting optional choices/constructor variants with unclear combinations or side effects; guideline says *consider* builder for complex construction, especially side effects. Source S5.
- **Exceptions/context:** Simple constructor, cohesive domain arguments, direct configuration struct is sufficient; FFI signature; immutable consuming builder may be required to transfer ownership. Need construction callsites, required-vs-optional fields, defaults and validity.
- **Fixtures:** Fail: users must select among many positional boolean-heavy side-effecting constructors with invalid combinations. Pass: builder takes required inputs and names optional configuration; small `Point::new(x, y)` remains unchanged; explicit configuration struct with validation.
- **Dedup:** API07 first for ambiguity. No arbitrary “more than N parameters needs builder”, no universal non-consuming builder mandate.

### API26 — Preserve already-computed useful results when demonstrated callers need them
- **Trigger/why:** Public operation discards a useful result it already computed and callers perform the same expensive lookup/parsing again to obtain it. C-INTERMEDIATE explicitly says consider exposing results potentially interesting to clients. Source S6.
- **Exceptions/context:** No demonstrated client need; exposing implementation would damage abstraction; rare extra work does not justify API expansion; callbacks already expose it. Need callsites and evidence of duplicate work.
- **Fixtures:** Fail: insert replaces old value but returns unit and caller must lookup old value before inserting. Pass: returns prior value akin HashMap::insert; boolean query stays boolean when no richer result is used.
- **Dedup:** Opt-in optimization/API review. Not speculative “return every intermediate value.”

### API27 — Fallible/blocking teardown has an explicit completion path
- **Trigger/why:** Drop panics on routine close/flush failure or hides an important failure only discoverable in destruction; blocking teardown has no explicit alternative where users need control. Guidelines note destructors execute during unwinding and a failing destructor can abort. Source S4.
- **Exceptions/context:** Best-effort drop fallback may ignore/log errors after explicit close was available; limited blocking may be resource-contract necessity; do not require observability/extra methods where there is no meaningful teardown failure. Need resource ownership, Drop body, actual failure/blocking and existing close/finish/shutdown.
- **Fixtures:** Fail: Drop calls `flush().unwrap()` on ordinary disk failure. Pass: `finish() -> Result` exposes failure, Drop performs nonpanicking best effort; explicit preparation avoids unexpected blocking.
- **Dedup:** Memory/runtime slice likely owns this; API slice explains public completion/error interface only.

## Preferences to exclude as universal rules

1. **Fixed function line counts, parameter counts, nesting/cyclomatic thresholds:** no official universal numeric limit found in the cited sources. The Book supports separating responsibilities, not arbitrary size enforcement. Thresholds may be explicit project policy, not Rust consensus.
2. **No unwrap/expect/panic anywhere; no panics in any library:** contradicted by Book's tests, prototypes, proven invariants and documented programmer-error contracts. API docs' preference for ? is narrower than a language-wide ban.
3. **Always anyhow in applications / always thiserror in libraries / never anyhow in libraries:** no universal crate choice follows from Book, std or API Guidelines. Error meaning, source preservation and public recovery needs matter; crate implementation mechanism is secondary. No security-guide anti-anyhow assertion is adopted here.
4. **Always typed errors instead of dyn errors, or always Box<dyn Error>:** official guidance supports meaningful error types and useful trait-object bounds but does not universally prescribe representation. Library extension/evolution, app reporting, no_std, allocations and MSRV decide.
5. **Always generics; never dyn; dyn always allocates; all traits must be dyn-compatible:** contradicted by documented code-size/heterogeneity/signature tradeoffs and Reference trait-object pointer forms. &dyn uses borrowed indirection, not inherently allocation.
6. **Ban traits/interfaces with one current implementation; require traits for every dependency:** current implementation count alone says nothing about a public extension point, associated-type contract or std interoperability. No universal minimum implementation count or dependency inversion mandate found.
7. **Every primitive/bool/Option needs a wrapper; every state machine requires typestate:** Guidelines motivate distinguishable interpretations and invariants; natural booleans/options and simple private code remain legitimate. No forced abstraction.
8. **Every constructor needs a builder; every builder must borrow mutably:** C-BUILDER is explicitly conditional, and consuming builders are documented for ownership transfer.
9. **All fields must be private; every public enum must be non_exhaustive; all traits sealed:** passive public records, intentionally closed enums and open extension traits are legitimate. Adding restrictions later can itself be breaking.
10. **Clone/Copy/Default/Eq/Ord everywhere; every error Send+Sync+'static:** guidelines say common traits are applicable and thread-friendly errors are useful; resources, NaN, local runtimes, lifetimes, MSRV and no_std invalidate blanket prescriptions.
11. **Serde/bitflags dependency mandatory:** API Guidelines recommend interoperability and correct flag representation, but choosing additional dependencies requires actual serialization/combined-flag use, target and dependency policy. Do not add dependency for a lint preference alone.
12. **Every public item needs a duplicated runnable example; doctests may never ignore/no_run:** guideline explicitly allows reasonable linked examples, rustdoc gives no_run for external effects and compile_fail for intentionally invalid code.
13. **Always test private functions / never test private functions; fixed coverage target / framework requirement:** Book explicitly acknowledges differing testing ideology and supports both unit/private and integration/public perspectives, not one mandatory ideology.
14. **Always use main.rs + lib.rs, a specific module depth, one type per file, mandatory facade/hexagonal architecture:** Book teaches a useful binary separation pattern when concerns grow, not a universal crate architecture. Modules group related code and control privacy.
15. **Always semver-major for MSRV increase; application semver exactly follows Rust signatures:** Cargo marks MSRV possibly-breaking and generally recommends minor; applications choose/document interface commitments. Runtime behavior changes remain maintainer judgment.
16. **Always prohibit glob imports, even use super::* in tests:** Cargo warns external-crate globs are a forwards-compatibility hazard; Book itself uses use super::* in unit tests. Scope matters.
17. **std import or extern crate means bad no_std:** no_std changes implicit linking/prelude, does not prohibit explicit std for supported configurations/tests; extern crate alloc is normal even in modern editions.

## Suggested minimal rule grouping and prioritization

Start with evidence-rich semantic checks: expected-failure panic policy (API01/02), error boundary context (API03/04), conversion contracts (API05), validated invariants/domain ambiguity (API06/07), accurate public contracts (API17), compatibility promises when a baseline exists (API21), meaningful test assertions (API23). These cover concrete harm without imposing personal style.

Ownership/API08, teardown/API27 and unsafe-documentation portions overlap the memory/runtime slice: assign one owner and cross-reference rather than emit duplicate findings. Treat method placement, builder adoption, generic broadening, common trait availability and intermediate return values as contextual API review suggestions unless actual misuse/cost is established. Fold static convention checks into tool preflight instead of an LLM naming/style pack.

Required context for any future evaluator: Cargo manifest/workspace and crate role; actual exported reachability/reexports; relevant implementation and callsites; docs and safety/error contracts; test/docs examples; cfg/feature/target/MSRV support; prior API/release intent for compatibility. If missing, abstain or explicitly request context internally rather than fabricate a violation.

## Jevlint capability gate (reported by parent capability research)

The current extractor supplies Rust function/type extraction and limited same-file related type/impl context, **not** compiler typing, name resolution, macro expansion, public-module reachability or complete call graphs. Method calls and `Type::qualified` calls do not resolve into direct callee context. Attributes can interrupt leading-doc capture. This is a concrete delivery constraint, separate from whether an ecosystem practice is worthwhile.

- **Potential narrow defaults only after fixture validation:** local, explicit contradictions observable in extracted source (for example From explicitly panics on an input branch; expected-user-input parse followed by panic when provenance is visible; test plainly discards its relevant result). Even these require validated resolution-free wording: a method named unwrap or a trait named From is not automatically the std item.
- **Advisory/opt-in with supplied context:** API01/02 when provenance or invariant comes from another function; API03/04 at cross-module error boundaries; API06/07 when constructor/accessor/state coverage is incomplete; API08/11 ownership and caller requirements; API14/15 complete coercion/trait-law reasoning; API17/18 public docs completeness; API19/20 API visibility and downstream extension intent; API22 feature support; API24/25 architectural suggestions.
- **Baseline/tool-assisted or manual, not reliable default:** API21 compatibility; exported-public-interface discovery; macro-generated API/contracts; unsafe/global proofs; Send/Sync capability; no_std target support; full invariant preservation across all construction/deserialization/FFI paths.
- Missing or truncated docs are **not evidence** of absent documentation. A fixture must prove doc/attribute extraction before enabling a documentation-presence judgment; missing headings already belong to Clippy/rustdoc.
- Function structure here means predictable operations, coherent ownership/error contracts, meaningful types and deliberate boundaries per API Guidelines, plus Book-backed separation of responsibilities where it has an actual benefit. It does **not** mean a numeric size limit, mandatory builder/facade or one-implementation-trait prohibition.
